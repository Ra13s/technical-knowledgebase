# KB intake — 2026-09-18

## Synthesis

The strongest pattern in this run is that **organizational context becomes substantially more useful when it is packaged as an executable capability instead of passive context**. LinkedIn's CAPT, DoorDash's Flux and Spring AI Community's Agent Skills all converge on progressive disclosure: initially expose only enough metadata for an agent to discover a relevant workflow, then load the instructions/tools when the workflow is actually selected. LinkedIn goes further and hides a growing tool estate behind a tiny set of meta-tools; DoorDash makes each playbook declare tools, permissions, validation and safety boundaries. The reusable architecture is not “put more company docs in the prompt.” It is “turn repeatable expert procedures into versioned, discoverable workflow contracts and let deterministic infrastructure enforce their capabilities.”

That gives us a better boundary between **knowledge, judgement and authority**. A domain expert can encode how to investigate an incident or clean up an experiment. The model still decides how to reason within that workflow. But the playbook/platform decides what inputs exist, what tools are available, which deterministic checks must pass and which side effects require approval. This also makes institutional knowledge more model-independent: a playbook can be invoked from an IDE today, a background agent tomorrow, or a scheduled workflow later without copying the same giant prompt between surfaces.

Datadog's DODO exposes the complementary problem: even a perfectly structured agent loop fails if its oracle rewards the wrong thing. Their optimization system first creates a benchmark from real production inputs and CPU-profile shape, iterates until the benchmark resembles production, then **freezes the benchmark before allowing the optimizer to edit service code**. This upgrades our existing search-based optimization pattern from “correctness gate + benchmark” to “prove the benchmark is representative + freeze it + optimize.” The general lesson reaches beyond performance: deterministic verification is only trustworthy when the verifier itself is grounded in the environment we care about.

Two non-agent findings show the same migration principle in conventional platform APIs: change the implementation boundary without forcing a flag day in consumers. Java 26 puts HTTP/3 behind the familiar `java.net.http.HttpClient` with explicit discovery/fallback policy, so we can canary H3 and observe `response.version()` rather than switching HTTP stacks. Kubernetes 1.37 lets DRA satisfy existing extended-resource requests, so a platform team can migrate device allocation node-by-node while workloads continue requesting the same `example.com/gpu` resource name. In both cases the useful engineering move is **preserve the contract, change the backend, measure the boundary**.

```text
repeatable expert workflow
        |
        v
playbook / skill metadata ----> on-demand discovery
        |
        v
explicit inputs + tools + permissions + validation
        |
        +--> deterministic policy / sandbox / gateway
        |
        v
model judgement
        |
        v
measured evidence / output

and for optimization:

production signals
   -> build representative oracle
   -> freeze oracle
   -> search candidates
   -> correctness + fitness gates
```

## New things we can use now

### Encode organizational workflows as executable agent playbooks

New canonical entry: `topics/ai/executable-agent-playbooks.md`.

Use a playbook as the deployable unit for a recurring engineering procedure: explicit inputs, context references, agentic/deterministic steps, tools, permissions, validation, outputs and safety boundaries. Keep the model-facing catalog small through progressive discovery. Enforce declared capabilities at a gateway/sandbox boundary rather than treating permission metadata as a polite request to the model.

The entry also includes a concrete Spring implementation option using the Spring AI Community `spring-ai-agent-utils` `SkillsTool`, while explicitly keeping sandbox/permission enforcement outside the skill itself.

### Java 26 HTTP/3 with `java.net.http.HttpClient`

New canonical entry: `topics/java/java-26-http3-httpclient.md`.

Use `HttpClient.Version.HTTP_3` to opt in and `HttpOption.H3_DISCOVERY` to choose between normal fallback-friendly discovery, `ALT_SVC`, and strict `HTTP_3_URI_ONLY`. Record `HttpResponse.version()` during rollout because preferred protocol is not evidence that H3 was actually negotiated. The entry calls out HTTPS-only behavior, proxy downgrade/failure semantics and JDK 26's non-LTS status.

### Migrate Kubernetes extended resources to DRA without changing workloads

New canonical entry: `topics/platform/kubernetes-dra-extended-resource-migration.md`.

Kubernetes 1.37 makes DRA-backed extended resources stable. Map an existing resource such as `example.com/gpu` onto a DRA `DeviceClass` and migrate node pools incrementally while existing Pod manifests continue using `resources.requests`. Move workloads to explicit `ResourceClaim` APIs later only where richer DRA semantics justify the application change.

## Existing KB entries improved

### Search-based code optimization agents with hard fitness gates

Datadog DODO adds a missing stage to the existing Meta KernelEvolve pattern: **validate the fitness function before searching it**.

The entry now recommends two separate loops:

1. generate a benchmark from safe production-derived inputs/state and production profiler shape until an explicit similarity target is reached;
2. freeze that benchmark, then let the optimization agent edit only service code.

It also adds hardware/runtime parity, pre-search flake fingerprinting, dense production-vs-benchmark profile diagnostics and retaining the best validated patch instead of trusting the last agent edit. Datadog reports three deployed DODO optimizations already reducing more than 8% of one mature service's total CPU cost, but the entry treats that as feasibility evidence rather than a transferable speedup claim.

### Intake policy

`prompts/knowledgebase-intake.md` now explicitly records this repository's **2026-01-01+ freshness boundary**. Older material may support verification of a 2026 finding but should not originate a new intake item. Forks are told to choose their own horizon deliberately.

## Valuable agent-system designs discovered

**LinkedIn CAPT:** particularly strong evidence for treating organizational expertise as executable infrastructure. LinkedIn combines central and repository-local playbooks, exposes them through MCP, and replaces a huge direct tool catalog with runtime discovery/inspection/execution meta-tools. Their reported scale — 500+ playbooks and 1,000+ engineers — makes this more than a prompt-pattern anecdote.

**DoorDash Flux:** useful because the playbook is only one of four explicit platform primitives: playbook, sandbox, MCP gateway and invocation surface. The strongest reusable detail is that the playbook declares required tools while the gateway grants scoped permissions and logs every action; workflow metadata feeds deterministic authority rather than replacing it.

**WorkOS Horizon:** a newly discovered source outside the normal radar. It independently reinforces several existing KB patterns: keep orchestration/control-plane state outside disposable sandboxes, broker short-lived credentials, proxy egress, use different sandbox flavors for planning/code/verification, and turn recurring agent friction into improvements to the shared context/tool surface. No new canonical page was needed because the architecture maps cleanly onto our existing deterministic-outer-loop and environment-containment entries.

## Rejected / deferred

**Spring AI `TodoWriteTool` and subagent orchestration:** concrete and reusable, but the repository already has stronger canonical patterns for external durable state, decomposition and bounded subagents. The Agent Skills portion added a genuinely distinct implementation primitive; the rest is logged as useful adjacent material rather than split into more pages.

**Kubernetes 1.37 scheduler preemption for in-place resize:** potentially useful, but still Alpha and narrower than the stable DRA migration bridge selected for this run.

**DRA fractional capacity / newer scheduling features:** relevant for accelerator-heavy platforms but not necessary to use the stable extended-resource migration path. Revisit when a concrete GPU-sharing requirement appears.

**Java Weekly #663 / This Week in Spring (Sep 15):** useful radar sources, but their other linked items did not beat the admission/value bar of the primary-source findings selected here.

## Experiments worth trying

1. **Playbook one real workflow:** take one recurring internal procedure that currently needs a checklist plus multiple systems, encode explicit tools/permissions/validation, and compare it against a free-form agent prompt on the same tasks.
2. **Spring `SkillsTool` pilot:** create one repository-local `SKILL.md`, expose only skill metadata initially, and measure context size/tool-selection behavior while keeping scripts inside the normal execution sandbox.
3. **Production-grounded Java optimizer:** for one CPU hotspot, combine sanitized representative inputs with JFR/profiler call-shape evidence, freeze a benchmark once it resembles production, then compare one-shot optimization vs bounded search.
4. **HTTP/3 canary:** enable JDK 26 H3 for one external endpoint, record negotiated `response.version()`, latency/fallback/error rate and proxy behavior, then decide from observed traffic rather than protocol enthusiasm.
5. **DRA compatibility pool:** migrate one accelerator node pool to a DRA driver with the same extended-resource name and run existing unmodified workloads against both legacy and DRA-backed nodes before expanding.
