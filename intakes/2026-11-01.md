# KB intake — 2026-11-01

## Synthesis

The strongest finding this round is an architectural separation worth making **explicit in our own automation**: an agent may be good at discovering useful engineering knowledge, yet it should not be the component that decides or exercises the final write permission. The Microsoft Aspire team published a working example of the boundary, not just a permission diagram. A merged product PR triggers deterministic routing to the appropriate documentation release branch, the agent reads a bounded diff and drafts the change, and a separate Safe Outputs stage creates a constrained cross-repo PR for the feature's original reviewer. Their published 30-day sample recorded 396 product PR events, 82 documentation PRs and 82 eventual merges with a 44.8-hour median lead time. It is particularly relevant to our knowledgebase, where scheduled research has historically succeeded while external publishing failed or required later repair. That experience is an *analogy*, not a measurement of what moving our workflow into GitHub Actions would achieve.

A second source challenges the assumption that an LLM-generated JSON result is somehow safer than a tool call. A research team systematically traced **Prompt-to-Agent** paths (untrusted issue/PR text becomes instructions to a privileged model) and **Prompt-to-Script** paths (model-derived outputs become commands or other privileged inputs to downstream CI steps). In their agentic-workflow sample, 496 of 519 flagged cases passed their exploitability test under the authors' threat model. That deserves attention even though their tool is not yet validated on our own workflow and disclosure/confirmation data remain limited. The common architecture across GitHub's production system and this independent analysis is therefore: **taint enters at data intake, all proposed effects stay untrusted, and the last trusted executor validates the exact side effect before acting**. Sandbox and read-only inference are useful, but so are strict output schemas, path restrictions, a bounded write budget and branch protection.

The strongest non-agent API discovery is Temporal's new **Standalone Nexus Operations**, with Public Preview beginning November 1, 2026. An ordinary Java service can start a durable cross-service operation using `NexusClient.newNexusServiceClient` without introducing a caller Workflow that exists only to make one Nexus call. The handler implementation can be reused from other Workflows. This fills a specific gap in the KB's existing durable-agent and document-ingestion material: call durability can be a shared application primitive rather than custom retry loops or an entire new orchestration tier for one operation. The material caveat is at-least-once execution, not magic exactly-once business effects. Stable operation IDs, idempotent handlers and an application-side recovery state remain required; the Java surface is explicitly experimental.

Finally, a GitHub Copilot code-review migration offers a valuable negative result. The team replaced specialized repository-navigation tools with more generally reusable `glob`, `grep` and `view` commands, and review performance initially became worse. Rewriting the review instructions to start from the diff, batch discovery and read only focused evidence reversed the regression, reportedly saving about 20% of average cost at comparable review quality. This strengthens our existing bounded-search and harness-ablation entries: **tool quality cannot be evaluated independently of the search behavior it induces**. Traces, search fan-out and actual accepted findings matter more than a tidy agent-tool API.

~~~text
untrusted source
  -> bounded discovery and evidence
  -> model decides a proposed change (tainted intent)
  -> trusted schema/permissions/path/revision checks
  -> separate execution capability (CI, PR, durable operation)
  -> exact authoritative state + tests + human review where required
  -> accepted artifact / reconcile, never blind replay
~~~

## New things we can use now

**[Compiled agentic workflows with Safe Outputs](../topics/ai/compiled-agentic-workflows-safe-outputs.md).** GitHub's `gh-aw` can compile an agent workflow and mediate its outputs through a separate allowlisted stage. The Aspire case includes a full cross-repository branch-routing and reviewer-handoff topology, scoped GitHub App identities, protected files and measured results. Prototype this as an alternative publication channel for our KB only after a dry-run and explicit permission review. Important: the convenient organization `GITHUB_TOKEN` Copilot inference path is **not** documented for this personal repo.

**[Agentic CI taint-flow audit](../topics/ai/agentic-ci-taint-flow-gates.md).** Add a source-to-sink security check for GitHub event text, generated agent outputs, shell steps and privileged GitHub actions. Use warning-only detection first, then prevent direct model-to-shell interpolation or unrestricted write tools. Keep static findings distinct from proven exploits.

**[Java Standalone Nexus durable operations](../topics/platform/temporal-standalone-nexus-java.md).** Concrete Java 1.36.1+ client API, local Temporal CLI 1.9+ runner, stable operation IDs, async result handles, and a Spring-style HTTP recovery pattern. Suitable for a bounded prototype; not yet GA.

## Valuable agent-system designs discovered

**Microsoft Aspire + GitHub Agentic Workflows (July 2026):** event-sourced trigger from merged feature PR; deterministic milestone-to-target-branch resolver; read-only agent with domain doc-writer skill; output as a constrained, draft-only cross-repo PR; automatic SME reviewer assignment and source-PR back-link; human review and normal merge rules. The core innovation is moving uncertain *content creation* into the model while preserving deterministic decisions on where changes land and who may approve them. The reported 82/82 merged docs PRs is encouraging but limited to one team's workflow and does not measure escaped documentation errors.

**GitHub Agentic Workflows security architecture (March 2026):** isolated credentials and outbound connections; compiled configuration; buffered safe outputs; trusted post-processing to filter operations, moderate or sanitize content and limit action volume. This provides a concrete isolation and execution topology for a repo-agent product instead of a mere prompt convention.

**Temporal cross-framework and service integration (October 26–30, 2026):** general-availability agent SDK integrations use replay-safe Workflows and external Activities, with framework retries coordinated by Temporal; Standalone Nexus separately allows non-Workflow callers. They show a common theme: agents/services can retain their preferred *inner API* while recovery moves to infrastructure. They do not make every framework behavior or external business side effect automatically deterministic.

## Experiments worth trying

1. **Separate planning from publication.** Build a minimal `gh-aw` workflow in a sandbox repository that reads 10 public engineering sources, proposes exactly one PR through Safe Outputs, and can neither edit protected files nor publish directly. Compare a repeated run and a simulated write failure against the current connector workflow. Measure accepted KB entries, duplicate-source rate, manual repair, wall time and cost.
2. **Taint-flow fixture set.** Audit one agentic CI workflow with benign and injected issue text, malformed generated output, unauthorized base branch and an attempt to leak model results into downstream scripts. Assert actual blocked GitHub effects, not just model refusals. Keep static-analysis false positives and dynamic outcomes separate.
3. **Java Nexus crash test.** Run the published sample with distinct caller/handler Namespaces. Kill the caller immediately after `start()`, verify a later query retrieves the same result by operation ID, then kill the worker during execution. Send two requests with one idempotency key and verify one external business effect.
4. **Diff-first reviewer ablation.** Keep model and tools fixed while toggling the old general browsing instructions vs targeted diff-first batched discovery. Evaluate on 30–50 historical PRs, including false-positive and missed-defect labels; compare review quality, grep/glob/view call counts, tokens and p95 runtime.
