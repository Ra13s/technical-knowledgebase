# Intake — 2026-09-10

## Synthesis

The strongest pattern in this run is that a coding-agent **harness has become a real software supply-chain and security surface**. Persistent instructions, skills, hooks, MCP declarations and permission files can change what a privileged agent reads and executes just as materially as a library dependency or CI configuration. A new empirical study makes the problem concrete: among 2,660 assembled public-repository setups, 16.0% carried a confirmed security defect under the study's validated rule set. The important failures were mundane and therefore reusable as engineering rules: floating MCP executables, interpreter grants that only look scoped, and reusable skills that silently pre-approve shell access.

That pushes our existing deterministic-outer-loop model one layer earlier. Correctness and safety do not begin when the model starts reasoning. They begin when the harness is installed and assembled. We should therefore treat agent configuration like IaC/package configuration: pin runtime-loaded dependencies, lint exact structural/capability defects in CI, inspect third-party skills before installation, and keep heuristic findings advisory until their consequence is validated.

The second layer is **context jurisdiction**. DaShaun Carter's Spring AI `AGENTS.md` work shows a practical way to keep repository instructions deterministic in a monorepo: resolve them from the target path, compose broad-to-specific ancestor guidance, refresh the applicable set when filesystem tools move the agent, cap how much instruction text can enter context, and emit resolution telemetry without logging the instructions themselves. This turns “give the agent repository context” from an ever-growing prompt into a scoped retrieval mechanism.

The final layer is the hard runtime boundary. Anthropic's containment post supplies unusually concrete failure evidence for why model safety and approval dialogs cannot be the final control: project-local configuration executed before a trust decision; a controlled phishing prompt exfiltrated credentials in 24/25 retries; and a hostname allowlist still permitted exfiltration through an approved API using an attacker-owned credential. The common fix is environmental: keep unnecessary credentials out of the sandbox, canonicalize paths before authorization, deny network by default, bind allowed API traffic to scoped identity, and establish repository trust before executable local configuration is loaded.

Together these findings suggest a useful full-stack harness architecture:

```text
third-party / repo harness artifacts
            |
            v
install + assembly static gates
  pins / grants / metadata / hooks
            |
            v
trust decision before local config execution
            |
            v
path-scoped + bounded instruction resolution
            |
            v
        model loop
            |
            v
sandbox / filesystem / egress / credential boundary
            |
            v
CI + exact approvals + publication gates
```

The broader implication is not “add more security prompts”. It is almost the opposite: **move deterministic policy out of prompts wherever possible**. Prompts and classifiers guide probabilistic behavior; static gates and runtime containment define what can actually happen.

## New things we can use now

### Gate coding-agent harness configuration as a supply chain

Add separate checks when reusable skills/config are installed and when the final repository harness is assembled. Gate only validated, byte-decidable defects; keep context-dependent cross-file observations advisory. A directly usable implementation is `harness-eval` with `harness-gate`, `harness-security`, `skill-verify`, baselines and SARIF output.

Canonical entry: [`Gate coding-agent harness configuration as a supply chain`](../topics/ai/agent-harness-supply-chain-gates.md)

### Resolve repository instructions by target path

For nested `AGENTS.md`-style guidance, resolve only ancestor instructions relevant to the active target, compose broad-to-specific, re-resolve after filesystem movement, impose explicit document/context limits, and expose low-cardinality resolution telemetry without instruction contents.

Canonical entry: [`Resolve repository instructions by target path`](../topics/ai/path-scoped-repository-instructions.md)

### Contain coding agents at the environment boundary first

Treat filesystem, process, network and credential restrictions as hard environment properties. In particular: defer project-local executable config until trust, keep credentials outside the sandbox where possible, resolve symlinks before path authorization, and treat an egress allowlist as a capability grant rather than merely a hostname list.

Canonical entry: [`Contain coding agents at the environment boundary first`](../topics/ai/environment-first-agent-containment.md)

## Valuable agent-system designs discovered

- **`harness-eval` / Red Hat research pipeline**: separates exact deterministic rules from advisory heuristics and validates a rule's consequence before promoting it to a gate. That quality discipline is as reusable as the individual security checks.
- **Spring AI Repository Steward**: refreshes path-scoped instructions as tools move through the repository, while the application — not the model — owns path safety, stale-write protection and final application of a change.
- **Anthropic containment stack**: uses different isolation strengths for different oversight assumptions and explicitly treats environment, model and external content as separate defense surfaces.

## Rejected / deferred

- **Spring AI in-JVM inference with ModelJars/Models** is genuinely actionable: a model can run inside the application JVM with Spring AI, and the recipe exposes important JIT/Vector API launch details. It is retained as an experiment candidate because the library/model-artifact ecosystem is young and the three harness/security patterns have broader immediate reuse.
- **Vectors VCR Test Harness** provides concrete record/replay wrappers for Spring AI and LangChain4j model calls, enabling offline CI without API keys. This is a strong future testing entry, but it needs a dedicated look at cassette integrity/staleness and what replay can and cannot validate before we canonize it.
- **Craig Walls' Efficient Tool Use** is good implementation evidence for the existing Spring AI ToolSearch entry rather than a new technique.

## Experiments worth trying

2. Add a pre-install `skill-verify` step for third-party coding-agent skills, analogous to dependency/security review.
3. Build a small path-scoped instruction resolver fixture with root/backend/frontend guidance and verify that tool movement changes the effective instruction set deterministically.
