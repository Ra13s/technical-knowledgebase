# KB intake — 2026-10-24

## Synthesis

The common lesson across this intake is that **agent safety is a chain of independently enforceable contracts, not a single system prompt or permission dialog**. AWS's experimental Strands Box and Eon's production MCP gateway attack different points in that chain. Box limits what an untrusted process can reach at the OS level, then applies operation- and history-aware Dogwood policy at trusted tool, interpreter and egress boundaries. Eon routes many human and autonomous-agent clients through one identity-aware MCP gateway that decides *who* may call *which exact tool*, and keeps downstream credentials outside each developer's local MCP processes. In both, the model can choose an intended action, but it cannot be the final authority that permits the effect.

The boundary details matter more than the slogans. Box's temporal policies see instrumented shell, HTTP and MCP events but **not every directly granted file access**; therefore a history-aware rule such as “do not upload after reading a secret” is only as strong as the event interception coverage. It is also a macOS Apple-silicon developer preview, not a portable server isolation product. Eon's gateway solves a different problem—shared identity and manageable tool catalogs—but introduces a central availability and policy-management dependency. It had to solve OAuth client compatibility, cross-account target identity, and a surprising scalability trade-off: pre-indexed schemas inflated its Cedar policy, whereas dynamically discovered tools reduced policy size but lost built-in semantic tool search. Neither solution replaces the target service's own IAM or the need to inspect the exact result of a mutation.

AWS's new EKS agent-observability walkthrough supplies the visibility piece: propagate `traceparent` from agent runtime through the model gateway, emit OpenTelemetry spans and structured cost/tool dimensions, and choose between direct OTLP export and a managed collector pipeline. Yet this **does not** change the authority hierarchy already established in our KB. An agent span claiming “PR created” is still not as trustworthy as a gateway authorization decision plus GitHub's actual resulting PR/ref state. The resulting reusable architecture is OS isolation, trusted per-operation policy, scoped identity/credentials, correlated outside-the-model execution evidence, and independent postcondition checks—each with its own failure tests.

An unexpectedly useful non-agent parallel comes from GitHub's star-history API. It is possible to cap an API response to 30 weeks while still scanning a repository's *entire* history on every request if `GROUP BY` happens before pagination. GitHub instead binds a calendar-week range before aggregation, shrinking the full-history work in its cited example from repeated scans totaling millions of rows to roughly one pass over current stars. The broader lesson is analogous to tool policy: **put the expensive or risky bound before the operation, not after it**. Here that means indexed `WHERE created_at >= start AND created_at < end`, then grouping, plus an explicit domain contract: historical star counts reconstructed from *currently existing* stars are not a complete record of stars that were later removed. Unlike the agent case studies, this is a directly testable SQL/API optimization for a Java/Spring backend.

We therefore gained three practical interventions rather than another generic “secure agents” essay: (1) test multi-tool and historical operation policies at the enforcement boundary, (2) centralize identity-scoped MCP discovery/authorization without assuming a tool manifest is an ACL, and (3) design bounded time-series query windows before aggregation. We also extended our authoritative-agent-telemetry entry with a concrete OTLP transport and correlation plan. Vendor performance and onboarding figures support *why to experiment*, not claims of measured benefit in our infrastructure.

~~~text
agent / IDE / unattended task
  -> OS sandbox (files/process/network ceiling)
  -> trusted tool or MCP gateway
       -> exact operation policy + per-principal identity + event history
       -> scoped downstream credentials; enforce again at tools/call
  -> API / shell / external effect
       -> trusted result + executor-side telemetry (correlated OTel trace)
  -> independent postcondition verification

time-series API:
  stable calendar window -> indexed range scan -> aggregation -> bounded response
~~~

## Valuable agent-system designs discovered

**AWS Strands Box + Dogwood (developer preview, October 7):** untrusted agent under macOS Seatbelt, trusted egress/command/MCP interception with a policy engine that can reason across tool event history, and credentials injected without giving the model the secret. This is an implementable experimental security harness; its macOS restriction, partial instrumentation and trusted-broker attack surface prevent treating it as a proven general solution.

**Eon multi-cloud MCP gateway (production account, October 20):** one governed tool surface shared by Claude Code, Cursor, Codex and an autonomous SRE agent. Human federation through Cognito, bot client-credentials, Cedar in ENFORCE mode, isolated AgentCore Runtime targets, versioned policy and downstream credential brokerage. Eon and AWS report more than 100 users/roughly 10,000 sessions and a shorter onboarding path, but not an independently validated security or escaped-defect rate.

**AWS EKS agent observability (implementation guide, October 21):** linked model and agent traces with an OTLP collector, plus instrumented model routing/fallback. We should reuse the collector, identity and metrics wiring while retaining an executor-side source of truth and measuring export completeness.

**Spotify Honk (independent production migration case, revisited):** dependency-based repository selection and verified field mapping for data migrations before passing targeted PR tasks to background coding agents. The case strengthens our existing executable-playbook and verification patterns but does not warrant an article-summary entry now.

## Experiments worth trying

1. **Multi-tool enforcement test:** on a supported macOS host, run Box with a synthetic MCP server and an HTTP tool. Attempt an unauthorized file read, prompt-injected network egress, an allowed read followed by disallowed upload, and a fourth permitted notification. Assert actual process/network effects and trusted event coverage, not only refusal text. Repeat on our Linux/container architecture with equivalent scoped egress.
2. **MCP gateway ACL matrix:** one developer JWT, one read-only audit bot, one write-limited SRE bot; fake GitHub, Kubernetes and Grafana endpoints. Test direct `tools/call` with tool names absent from discovery, expired/mismatched tokens, OAuth `state`, tool-list churn, and outages. Compare pre-indexed vs 300-tool dynamic manifests on startup latency and policy build size.
3. **Cross-plane agent trace test:** a model requests a GitHub write which fails in the executor. Ensure linked trace IDs and a protected audit record reflect failure regardless of what the model says. Test collector outage, sampling, dropped events, secret redaction and p95 cost.
4. **Bounded SQL work:** on 5–10 million skewed time-series rows, use `EXPLAIN (ANALYZE, BUFFERS)` to compare full-history group/offset, 30-week indexed ranges, and a rollup table; test viral-density weeks, timestamps, concurrent writes and deleted source rows. Require bounded p95 and correct API semantics.
5. **Revisit Cosmos DB CDC:** prototype a delayed/duplicated invalidation event crossing a region boundary. Assert caches never serve stale auth or critical metadata after a documented consistency window; define the actual data-plane guarantees before recommending a design.
