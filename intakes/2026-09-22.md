# KB intake — 2026-09-22

## Synthesis

The strongest pattern in this run is that **high-autonomy systems need explicit evidence objects, not inferred completion**. Google applies this to security review: an LLM finding is only a hypothesis until localized threat context, structural reachability or sandbox reproduction gives it evidence strong enough to interrupt a developer. Datadog applies the same principle one layer lower: an individual agent may be perfectly well behaved while the shared platform collapses under aggregate retries, queues or quota pressure, so every trajectory needs stable workload identity, an explicit service class and a bounded recovery contract. Kubernetes 1.37 applies it to hidden storage state: changing a CRD or encryption configuration does not mean old objects changed; `StorageVersionMigration` makes the rewrite a first-class API object with observable completion.

This extends several existing KB themes. We already bind agent edits to current evidence, approvals to exact side effects and CI to an exact head SHA. The new material suggests a more general rule: **attach identity, proof and lifecycle state to every important autonomous claim**. A security finding should identify its entry point, sink and verification evidence. An agent request should carry workload/owner/environment/service-class/run identity through queues and enforcement points. A data migration should have a resource, controller and `Succeeded` condition. “The model said so”, “the config changed” and “the request returned 200” are all too weak when the downstream state matters.

Google's security architecture is particularly useful because it separates *discovery* from *trust*. Cheap/semantic scanning is allowed to propose hypotheses, but a specialized stage checks AST structure, call-graph reachability and domain safety rules, and difficult findings can be reproduced inside a sandbox with explicit acceptance criteria. The patch agent then receives the proof and has to survive an adversarial re-test. This is stronger than merely asking another model whether the first model seems confident. Google's internal metrics show that this architecture can reach high precision at very large scale, while the open-source Mantis project explicitly warns that reproduction and patches still require expert verification. That distinction belongs in our design, not in fine print.

Datadog exposes a second failure mode that becomes important as coding agents move from demos to fleet infrastructure: **recovery itself is load**. Per-agent retry limits do not protect a shared provider, CI farm or sandbox pool when hundreds of agents retry simultaneously. Capacity planning therefore needs the whole trajectory, dependency-specific constraints, workload-class policies and two retry boundaries: one for how much recovery a single run may generate, and another for aggregate concurrency/queue pressure. The same workload identity should drive both observability and enforcement, including requests rejected before normal tracing middleware runs.

Google's new Agent Substrate reinforces our existing containment and fleet-economics entries rather than deserving a separate canonical page yet. Its strongest reusable ideas are already compatible with our model: keep credentials outside the agent sandbox and inject them at the egress boundary, use kernel/network isolation for generated code, and stop reserving CPU/RAM while autonomous sessions wait on model/tool/human latency. It is valuable implementation evidence, but the product/runtime is new enough that we should not turn its specific architecture into a universal recommendation.

## New things we can use now

### Gate agentic security findings with localized threat models and proof

New canonical entry: `topics/ai/agentic-security-presubmit-pipeline.md`.

For security review, scan the change with live code/threat context, then require a separate triage stage to prove reachability using structural evidence. Reproduce high-impact/ambiguous cases in a sandbox with explicit acceptance criteria, and give the resulting proof to the patch agent. A fix is not complete until the original reproducer and adversarial bypass checks fail safely.

### Protect shared agent platforms with workload classes and bounded recovery

New canonical entry: `topics/ai/agent-platform-capacity-isolation.md`.

Inventory the full trajectory rather than only LLM traffic, propagate workload/owner/environment/service-class/run identity to every hop, reserve or shed capacity based on workload criticality, and enforce retry budgets both per trajectory and at the shared-service level. Treat policy denial as terminal so guardrails cannot cause retry storms.

### Migrate stored Kubernetes API objects with StorageVersionMigration

New canonical entry: `topics/platform/kubernetes-storage-version-migration.md`.

On Kubernetes 1.37+, use stable `storagemigration.k8s.io/v1` objects after CRD storage-version changes or encryption-at-rest/key rotation. Gate retirement of an old CRD version on `Succeeded=True` plus the expected `.status.storedVersions`; if the CRD changes during migration and stored versions do not converge, rerun it.

## Valuable agent-system designs discovered

**Google pre-submit security + Mantis:** a strong whole-system example of semantic discovery followed by progressively harder proof: localized threat modeling, lightweight scanning, structural triage, sandbox reproduction, calibration, adversarial patch verification and human review. Its strongest reusable property is role separation: the component that invents a finding does not get to declare it true.

**Datadog agent-scale platform controls:** unusually concrete production guidance for what happens after agent adoption succeeds. Full-trajectory inventory, workload-class isolation, separate production/evaluation capacity, dual retry budgets, lifecycle-specific timeouts and identity-preserving enforcement form a reusable platform operating model.

**Google Agent Substrate:** useful implementation reference for secure/efficient ephemeral agent environments: microVM or gVisor isolation, network gateway credential injection outside the guest, pre-warmed workers, snapshots and active-only compute. Keep watching it as production availability and independent operating evidence mature.

## Rejected / deferred

**Java 27 runtime/security changes:** Java 27 is now GA and contains several concrete candidates — JFR in-process redaction, `VM.security_properties`, improved runtime diagnostics, post-quantum TLS and compact object headers by default. These are worth a dedicated Java-focused intake rather than turning this run into a release-note grab bag.

**More frequent Java security updates:** Oracle's move toward monthly security updates has real patch/test/release-pipeline implications, but the cadence is still transitioning. Logged as an experiment/candidate rather than a canonical rule today.

**Spring release-train changes:** operationally interesting ecosystem news, but it does not yet change what we would implement in an application or platform enough to pass the admission test.

**Agent Substrate as its own canonical architecture:** deferred because the reusable controls overlap our existing containment and fleet entries and the product is newly available; no need to make every shiny runtime its own species of Pokémon.

## Experiments worth trying

1. **Proof-gated security review:** run a security reviewer on 50 historical PRs with known findings; compare generic review vs localized threat context vs context + structural triage. Add reproduction only for surviving high-severity findings and measure precision/recall/cost.
2. **Dual retry budget chaos test:** generate 50 parallel agent runs against a dependency that returns 429/`Retry-After`; verify per-run limits plus shared concurrency/load shedding prevent retry amplification and preserve critical-service headroom.
3. **Workload identity propagation:** trace one agent task from trigger through model/tool/queue/CI/API side effects and verify `{workload, owner, env, serviceClass, runId}` survives both success and rejection paths.
4. **Kubernetes stored-version migration:** upgrade a test CRD on 1.37, migrate stored objects, deliberately modify the CRD during migration, and verify the rerun/`.status.storedVersions` gate before removing the old API version.
5. **Java 27 follow-up:** in the next Java-focused run, test JFR redaction and `VM.security_properties` on a real Spring service and decide whether they deserve focused canonical recipes.
