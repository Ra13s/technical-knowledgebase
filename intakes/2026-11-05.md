# KB intake — 2026-11-05

## Synthesis

This run reveals a useful architectural symmetry between systems that appear unrelated: **the reusable boundary is a small, deterministic contract around independently changing contributors**. Inkitt's PR creator uses a pure event reducer around short-lived coding-agent stages; Uber Freight builds one search document from domain-owned fragments; LinkedIn groups independent request traces into a user journey. None of the three relies on one omniscient component. Each gives independently operating units a common identity, a constrained contribution surface and an authoritative way to assemble or verify a larger result.

The strongest coding-agent design came from a smaller, previously untracked source: Inkitt Tech's August 26 account, independently surfaced by InfoQ on November 4. It does more than draw the familiar “agent inside deterministic outer loop” box. Each agent run is **one durable row**, and a *pure* `(state, event) -> next action` reducer decides whether to launch a specialist container, retry, stop, or reconcile CI. The executor owns credentials and side effects; stage containers are disposable. Conditional writes decide who wins a race to claim a branch or PR, while a complete GitHub check-suite query—not a single CI webhook—decides whether tests have finished. The design adds an important operational detail to our [durable agent effects](../topics/ai/durable-agent-tool-effects-and-fencing.md): a state machine can be unit-tested without LLMs, and interruption handling can be chaos-tested independently of code-generation quality. Inkitt reports daily shipping, not a controlled defect or cost study; we should validate the mechanics locally rather than adopt the success claim.

Uber Freight's October 27 engineering write-up makes the same idea concrete in **distributed data ownership**. Forty-plus services cannot all own an entire search document. Instead, each declares a fragment (source, field mapping, relationships); the platform owns bootstrap, CDC ingestion, index mappings and continuous source-to-index checking. The key non-obvious move is that bootstrap and streaming share the same fragment transformation, and fields have one declared owner. A service can change its own slice without reassembling unrelated slices on every update. LinkedIn's October 22 tracing article solves a related *identity* problem: a user page generates many separate request traces, so treating a single `traceId` as “the journey” is a category error. A page-context/forest ID groups traces without destroying request-local context, and a coordinated head-sampling decision prevents the client and server from independently discarding opposite halves of the same story. These are both immediately prototypeable, with caveats around CDC ordering, fan-out amplification, span loss and privacy.

We also found strong cross-checks for existing KB patterns. Uber's October 1 MCP Gateway **discovers APIs but does not enable them**: a crawler derives tool schemas from IDLs, registers them disabled and requires a service owner to review activation and description changes. It also exposes incremental tool discovery and CLI-based search to avoid filling model context with thousands of schemas. Google's PageBreak provides a distinct security validation lesson: non-model-written exploit validators confirm agent hypotheses on real authorized applications; unverified findings stay in an internal research queue instead of becoming developer noise. Neither story demonstrates universal safety. Both demonstrate why **discovery and permission**, or **hypothesis and evidence**, should be different states enforced by different actors.

~~~text
producer / model / service / client
       -> typed contribution (event, fragment, trace, candidate)
       -> stable identity (run, entity+owner, page, vulnerability class)
       -> deterministic constraint (transition, field owner, sampling, validator)
       -> authoritative evidence (GitHub/CI, source-of-record, correlated spans, repro)
       -> publish / update / alert only on verified conditions
~~~

The choice we can now make more confidently is **where to spend orchestration complexity**. Use the pure state reducer for externally observable workflow lifecycles; a common projector for shared search documents; and a journey identifier only when multiple traces are legitimately one user experience. Don't apply each pattern everywhere. A three-step local script does not need a durable workflow database; a single-table search does not need a fragment framework; and a single HTTP request already has a good trace identity. The expensive parts should be introduced only when their corresponding coordination failure is observable.

## Valuable agent-system designs discovered

**Inkitt (original post August 26, resurfaced November 4):** authenticated Slack/Linear/API intake -> pure event reducer with one run row -> short-lived spec/implement/verify/CI repair/conflict stage -> real diff and full GitHub CI gates -> draft PR and human review. Authenticated, deduplicated events, conditional state claims, two retries per detour and a strict restricted-path policy form a complete control topology. No stage gets the orchestrator's broad external credentials. The code and failure-rate data are not public, so our KB entry deliberately labels its SQL and reducer as prototype sketches.

**Uber MCP Gateway (October 1):** IDL registry + native server discovery -> Cadence AutoCrawler -> generated server/tool schema in disabled state -> service-owner review -> proxy gateway with per-tool authorization and HTTP/gRPC/TChannel translation; incremental Omni MCP/CLI discovery avoids context growth. The useful whole-system lesson is that *tool creation, owner enablement and runtime execution* should not be one permission decision.

**Google PageBreak (September 24):** agent-generated hypotheses -> class-specific deterministic application validators -> confirmed reports, with a separate internal backlog for unresolved/unreproduced cases. The 500+ XSS figure is a Google self-report without an independent recall benchmark; unreported candidates may still matter.

## Experiments worth trying

1. **KB publishing reducer:** build a small state transition reducer for `DISCOVERED -> PATCHED -> CHECKED -> PR_OPEN -> MERGED` and test 100 duplicate/out-of-order webhooks, a lost PR-create response and stale head commit. For real use, enforce a trusted publisher that queries GitHub instead of trusting a model-generated status; compare its operational burden to the existing connector.
2. **Three-fragment index canary:** join shipment, customer and stop tables into one OpenSearch index. Bootstrap a snapshot then replay CDC from the matching watermark; mutate one customer referenced by 2,000 shipments, delete a stop and inject out-of-order events. Track stale fields, fan-out amplification, QPS/latency and source/index discrepancies.
3. **UI trace forest:** instrument one web UI screen and a Spring backend with three independent requests, failure in one request, a time-bounded page-context header and a test collector. Verify trace grouping, head-sampling cohesion, sensitive-data redaction and exporter overhead under backgrounding.
4. **MCP schema activation gate:** derive disabled tool manifests from a tiny OpenAPI/Protobuf example, require owner approval for enabling/description changes and assert unauthorized direct `tools/call` is rejected even if the tool name is known.
5. **Security evidence split:** give a review agent 20 seeded vulnerabilities and matching non-vulnerabilities; only report findings with a deterministic, independently authored reproducer and keep unverified candidates in a separate backlog. Measure confirmed precision, known-bug recall, coverage gaps and reviewer time.
