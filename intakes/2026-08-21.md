# KB intake — 2026-08-21

## New things we can use now

### 1. JSpecify + NullAway for Spring 7 / Boot 4 null contracts

Added [`topics/spring/jspecify-null-safety.md`](../topics/spring/jspecify-null-safety.md).

Practical rule: make a package non-null by default with `@NullMarked`, mark the exceptional nullable type uses with JSpecify `@Nullable`, and enable NullAway for `@NullMarked` packages in the build. Migrate incrementally; turn on fuller `JSpecifyMode` only after the basic package contracts are clean.

This is particularly useful now that Spring Framework 7 and the Boot 4-generation portfolio expose JSpecify metadata themselves. The entry also records the easy-to-miss `TYPE_USE` array/generic placement rules and the javac constraints for NullAway's fuller JSpecify mode.

### 2. DuckDB inside a Spring Batch Tasklet for set-based transforms

Added [`topics/spring/spring-batch-duckdb-transforms.md`](../topics/spring/spring-batch-duckdb-transforms.md).

Practical rule: before writing a large Java in-memory aggregation/join loop, ask whether the transform is naturally relational. If it is, prototype an embedded DuckDB JDBC `Tasklet` and benchmark both approaches on representative input.

The canonical entry deliberately does **not** turn the published 6x–8x example benchmark into a general performance claim. It keeps the useful implementation shape and the decision boundary: DuckDB for analytical set transforms; item-oriented Spring Batch for per-record enrichment, side effects, retry/skip semantics and strict downstream writers.

### 3. One required GitHub Actions status check for conditional CI

Added [`topics/platform/github-actions-aggregate-required-check.md`](../topics/platform/github-actions-aggregate-required-check.md).

Practical rule: in monorepos/conditional CI, keep component workflows reusable via `workflow_call`, detect changed areas in one always-triggered caller, run relevant workflows conditionally, and make one final `status` job the only required check. Include `merge_group` when using GitHub merge queues.

This avoids both the “required workflow was path-filtered and never reports” deadlock and the maintenance problem of updating branch protection every time CI gains another job.

## Reviewed but not promoted

### Autonomous TDD inside the agent loop

Birgitta Böckeler's exploratory TDD evaluation is useful enough to influence an experiment, but the sample is intentionally small and all tasks were greenfield business-logic exercises. It did not show a clear outcome-quality or mutation-score benefit from forcing a full red/green/refactor loop, while the TDD runs used substantially more turns/tokens.

**Disposition:** `skipped-low-confidence` for canonical policy. Do not yet encode “agents should not use TDD” as a knowledgebase rule.

### IntelliJ ACP custom agents and Agent Skills

JetBrains now documents a concrete ACP boundary for custom agents (`~/.jetbrains/acp.json`) and project/global skills for Codex/Claude. This passes the actionable test, but it is narrower and more IDE-specific than the three selected additions.

**Disposition:** `skipped-lower-priority` this run. Revisit only if we start standardizing an IntelliJ-hosted agent workflow; otherwise the official docs remain the right reference.

## Concrete experiments

1. **Null-safety pilot:** mark one real Spring package with `@NullMarked`, add NullAway `OnlyNullMarked`, and record: compile-time findings, true defects, required suppressions, and migration effort. If clean, enable fuller JSpecify mode in that package.
2. **DuckDB transform benchmark:** take one aggregation-heavy batch transform and implement the same result both as current Java logic and a DuckDB SQL Tasklet. Compare wall time, peak memory, output equality, restart behavior and deployment/container friction.
3. **Aggregate CI check:** apply the single-status pattern to a repository with at least two path-conditional jobs. Verify four cases: frontend-only, backend-only, deliberate component failure, and merge-queue execution.
4. **Agent TDD A/B (do not canonize first):** run the same representative coding tasks with (a) autonomous TDD instructions and (b) upfront design + outcome tests, then compare human review findings, mutation score, unnecessary edits, turns and token use.
