# KB intake — 2026-10-16

## Synthesis

This run revealed a blind spot in the way teams validate autonomous coding: **functional correctness, contribution correctness and deployability are different contracts**. A patch can pass tests while the agent violated repository policies along the way; a UI prototype can work in a test environment while its unfinished code is still bundled into the production application; an observability upgrade can leave business behavior green while silently invalidating an alert. Each requires evidence from a different authority. The recurring engineering change is to put those contracts in **independent, observable gates**, not in one broad instruction to the agent.

The strongest research find is SWE-CC. Its authors took contribution instructions from 12 repositories, converted them into 823 checkable rules and evaluated 500 end-to-end agent tasks. They examined both the agent's **trajectory** and its **final contribution**; agents violated 43.1% of applicable policies in the study, with nearly half the violations occurring during execution. The lesson is deeper than “add more CI”: a PR diff cannot show that the agent attempted a disallowed operation or never ran a required test at the correct point. The harness needs externally captured events, versioned policy triggers and explicit `pass/fail/not_triggered/withheld` outcomes. This extends our existing evidence-gated-edit guidance from “prove the fix” to “prove the entire contribution met its contract.”

Meta's Forum case study shows the complementary **build artifact boundary**. The team uses a prototype-only app variant that shares real application infrastructure but excludes experimental modules from the production build, rather than trusting a runtime feature flag. It also gave agents access to actual simulator view hierarchies and repeatable UI stress scenarios. That connects to the KB's agent-addressable application-feedback loop: live semantic observation reduces wrong-screen work, recorded build/test/visual evidence makes review actionable, and a separate build target prevents unreviewed experiments from leaking into a release. The reported eight-week build and memory improvements are Meta-specific; what we can reuse is the variant graph, packaging assertions, and human acceptance boundary.

The Java finding is strikingly similar. OpenTelemetry Java agent 2.32.0 exposes the coming 3.0 conventions ahead of release, with selective `/dup` emission for comparing database and messaging telemetry. But duplicated attributes do not mean duplicated **span relationships, metrics or units**. A production deployment can be functionally healthy and observability-blind if an old database metric changes name or a messaging trace becomes linked rather than parented. The recipe is capture baseline -> test domain preview -> test changed defaults -> validate real alert intent -> canary -> release, with rollbacks tied to the exact instrumentation/configuration pair.

One caveat cross-cuts the agent results: independent sandbox testing by Riptides found that write confinement does not automatically stop sandboxed commands from reading inherited credentials or host files. We already have environment-first containment, so this evidence belongs there as a future negative-capability test, not as a second general sandbox article. Separately, Enola's October extraction refactor is an excellent example of byte-identical semantic-output tests catching unintended regressions, but we deferred another canonical testing page until a second system or our own experiment confirms the workflow's transferability.

```text
task + repository rules + exact code revision
  -> agent work (isolated, externally observed)
  -> runtime policy check + functional tests
  -> final-diff policy check + build artifact inspection
  -> runtime/UI/telemetry acceptance on the real target
  -> evidence attached to PR -> human or GitHub gate -> published result
```

## New things we can use now

**[Repository-policy and trajectory compliance gates](../topics/ai/repository-policy-compliance-gates.md)**: author atomic triggered policies, capture runtime tool events separately from agent prose, check the submitted diff independently, and report triggering rate alongside compliance rate. Prototype first on the KB intake workflow.

**[Compile AI-built prototypes out of production](../topics/ai/compile-out-prototype-app-variants.md)**: use separate production/sandbox dependency graphs and verify actual package contents. Agent-explorable UI and recorded regression evidence support promotion; a feature flag does not replace exclusion.

**[OpenTelemetry Java agent 3.0 preflight](../topics/platform/opentelemetry-java-agent-3-preview-migration.md)**: turn on domain dual emission in 2.32.0, compare names, values, units and trace topology, then test the combined default preview. Validate alert queries and sensitive structured fields before promoting the agent.

## Valuable agent-system designs discovered

**Meta Forum (production):** rules, dynamically loadable skills, specialized agents, composed commands and deterministic hooks support a supervised plan -> code -> test -> visual verification -> PR loop. The implementation-level innovations are simulator view-hierarchy inspection before acting, repeated app-like stress scenarios and sandbox-only build variants. Agent autonomy is bounded by proven verifiers and engineer approval, not measured in generated lines.

**SWE-CC (serious experimental harness):** contributor docs -> atomic policies -> deterministic checkers; agents run on pinned task environments; tool trajectories and final artifacts are audited separately. A benchmark-integrated CI/checker system can extend our current functional tests without having the model grade itself. The publicly released results don't include every raw historical trajectory, so full independent replay of the paper's experimental claims remains limited.

## Rejected / deferred

- **Enola TypeScript extractor:** concrete N+1 improvements, 124-repository regression suite and byte-identical snapshot comparison are promising. Treat as an experiment with our static-analysis/indexer tooling rather than adding another canonical performance page on one vendor's evidence.
- **AgentSWE:** hidden acceptance across agent creation/edit/optimization directly exposes overfitting and hollow implementations; defer a dedicated entry until the harness/reproducibility details are evaluated against our own agent-development tests.
- **Multi-agent energy paper:** measured large latency/energy penalties for generic multi-agent setups, but our existing harness-ablation and fleet-economics pages already call for task-specific ablations and outcome-denominated comparisons.
- **Spring Batch 6.1.0-M2:** useful new APIs, but milestone compatibility is not yet a preferred production default.
- **Meta Sapienz award:** validates repeatable multi-objective exploration at real scale but does not add a distinct implementation recipe beyond the agent UI testing pattern selected today.

## Experiments worth trying

1. Encode 8–12 KB intake rules as deterministic `pass/fail/not_triggered/withheld` checks; capture agent command events and PR artifacts on ten runs. See which violations were invisible to final-diff-only CI.
2. Add separate sandbox/production build targets to one UI app, deliberately inject an experimental module, and fail CI if the production import graph or shipped bundle contains it. Run the same user flow on the sandbox and promoted production build.
3. In a Java service instrumented with OpenTelemetry 2.32.0, compare baseline and 3.0-preview SQL and producer/consumer telemetry under repeatable traffic. Confirm alerts and traces still serve their intended diagnostic use.
4. Reproduce the Riptides negative-capability checks with disposable canary data: confirm that agent commands and tools cannot read unrelated host files or environment values.
5. Differential-test a code analysis/indexing refactor: freeze extracted facts over several representative repos and compare byte-for-byte except for reviewed additions; then measure cold and warmed performance.
