# Intake — 2026-08-25

## New things we can use now

### Spring Data type-safe property paths

Spring Data Core 4.1 / the 2026.0 line can replace static string property names with Java method references:

```java
Sort.by(Person::getFirstName, Person::getLastName);
```

Nested paths remain typed through `TypedPropertyPath`. This is a cheap refactoring-safety win: use typed paths for compile-time-known properties and keep strings only at genuinely dynamic boundaries.

Canonical entry: [`Spring Data type-safe property paths`](../topics/spring/spring-data-typed-property-paths.md)

### Spring AI structured output can validate and self-correct

Spring AI 2.0 adds two composable switches to typed `.entity(...)` responses:

```java
.entity(Result.class, spec -> spec
    .useProviderStructuredOutput()
    .validateSchema());
```

Provider-native output constrains generation upstream; `validateSchema()` catches malformed output in Spring AI and retries with the concrete schema error, up to three attempts by default. This replaces ad-hoc parsing/retry loops for important typed AI results.

Canonical entry: [`Spring AI structured output validation and self-correction`](../topics/spring/spring-ai-structured-output-validation.md)

### GPT-5.6 Programmatic Tool Calling for deterministic tool reduction

Programmatic Tool Calling is useful when a bounded stage needs many lookups plus filtering/joining/ranking/deduplication/aggregation but does not need fresh model judgment after every result. The generated JavaScript runs in a restricted hosted V8 runtime and may call only explicitly eligible tools.

The important decision rule is not “use PTC for lots of tools”; it is “use PTC when intermediate work is deterministic and reducible, keep approval/semantic/citation-sensitive calls direct.”

Canonical entry: [`OpenAI Programmatic Tool Calling for bounded tool-heavy stages`](../topics/ai/openai-programmatic-tool-calling.md)
