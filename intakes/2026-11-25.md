## Synthesis

There is a difference between measuring how much an agent got right and knowing that the thing it built actually works. JoyFrontBench makes that difference unusually visible: good average task scores coexist with substantially lower complete-application success. A practitioner writing about tests as data reaches the same issue from the maintainability side: if the implementer can freely rewrite both business expectations and their executable checks, passing CI is a moving target. Agenor's annotation-driven behavior case is a concrete example of tests and implementations agreeing while the real user entry point fails.

We should treat an acceptance contract as a versioned engineering input, not just another generated deliverable. Humans review compact scenarios and mandatory outcomes, the agent implements and writes developer tests, and an independently controlled runner verifies the exact candidate artifact. This extends our previous mutation-gate and reference-oracle entries: mutations answer whether tests detect defects; protected goal contracts answer whether we are still checking the intended behavior. Neither replaces the other. The benchmark is a preprint and the practitioner articles are not randomized evidence, so validate this with real journeys and seeded defects before making it a mandatory workflow.

Two smaller discoveries reinforce the importance of inspecting the thing itself. Dukehoff supplies semantic Java refactoring operations through the NetBeans engine, taking a step beyond our source graph: indexed text relationships are useful for locating a symbol, but compiler-resolved references are more suitable for overload-aware changes. Its own timings are not independent evidence; cold indexing and dynamic wiring still matter. Meanwhile Surefire's timeout extension gives us a rare chance to retain direct evidence of a hung JVM before CI tears it down. That changes a debugging task from guessing at a past failure to reading the blocked threads from the actual failure.

The shared practical lesson is not to add an extra reviewing agent everywhere. It is to make the thing being reviewed explicit, versioned and observable: the goal contract, the exact Java symbol, or the state of the timed-out process. Choose the cheapest reliable evidence and preserve it before it disappears.

## Valuable agent-system designs discovered

- JoyFrontBench provides a concrete evaluator topology with goal decomposition, evidence, deterministic record auditing and whole-artifact acceptance. Adapt its separation of partial progress and completion, not its exact scores.
- The Dukehoff server packages an existing Java IDE engine for agents. This is a useful example of delegating a narrow code transformation to an established deterministic subsystem rather than asking a model to reproduce its functionality.
- The Stock Replenisher durable-agent example on martinfowler.com separates action selection, state transition, waits and effects. It overlaps our existing durable tool effects and outer-loop guidance; no new page.

## Experiments worth trying

1. Freeze 10 user journeys with protected input/output expectations. Run current CI and the independent evaluator on the same intentionally defective artifacts; include a removed criterion and a forged record.
2. Compare grep/manual editing against Dukehoff on 15 Java overload rename, signature-change and namespace-migration tasks. Track correct references, build failures, reflection/config misses, cold/warm latency and review time.
3. Run one disposable Maven/Gradle CI job with known deadlock and latch timeout. Require failure plus useful artifact; compare pre-kill extension against a watchdog.
4. For a security-sensitive Java endpoint, pre-identify authorization checks in a held-out reference, then compare normal retrieval and safeguard-seeded context; verify deny behavior with independent negative tests. Do not equate merely reading a safeguard with preserving it.
