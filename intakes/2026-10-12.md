# KB intake — 2026-10-12

## Synthesis

This run's strongest connection is that **agent scale makes two kinds of correctness inseparable: evaluating probabilistic decisions on representative evidence, and constraining side effects to the smallest authoritative operation**. GitHub's ReviewBench demonstrates the first half. A useful reviewer evaluation cannot be based on a demo PR, unverified model-written findings, or comment volume. It needs frozen repository states, defects gathered independently from humans/models/static analyzers, a consistent rubric, and *two* scoring views: fixed known issues for comparable grounded recall, and newly validated issues that the incomplete gold set would otherwise miss. That is the evaluation counterpart to our existing precision-first multi-stage code-review architecture: before optimizing a scout, specialist or reviewer, we need an oracle that measures something developers actually care about.

The new empirical harness paper sharpens the second-order decision: the best architecture is not “more agents and more scaffolding.” It compared two harnesses, ten models and three task families, then isolated individual components in NanoHarness. Structured tools and task-specific subagents were comparatively reliable improvements; generic subagents and context compression could actively hurt repository generation. Complex harnesses bought less on localized SWE-style repair as the model improved but remained potentially valuable on open-ended tasks. This strengthens our existing one-component-at-a-time ablation rule by adding a **model × task family** evaluation matrix. A successful repair benchmark is not evidence that the same harness will help a greenfield implementation task.

Git 2.56 offers the deterministic counterpart in a surprisingly small API. The new `git add --resolved` stages only currently conflicted paths when selected regular files contain no conflict markers; if markers remain, it refuses to stage anything in that selection. It is explicitly not semantic validation—the file can be wrong without containing conflict markers, binary/deleted paths are a special case, and previously staged unrelated changes remain possible—but it reduces the accidental staging blast radius of conflict-repair automation. That is actionable immediately for agent worktrees and developers handling merges in dirty checkouts.

GitHub's separate October architecture write-up shows what happens at the next order of magnitude: agent fleets increase writes and CI read fan-out until a system that previously scaled by replicating complete durable repositories develops coordination and latency ceilings. Their proposed design minimizes coordinated work to authoritative reference updates, moves object work and maintenance off that serialized path, and splits durable storage from caching compute. That is valuable systems design, but still a forward-looking architecture backed by internal benchmarks, not a ready-made canonical recipe for a team not operating a Git hosting platform. Together, the sources reinforce a practical operating model: **freeze the evidence for judgement; narrow the mutation boundary; measure the real workflow rather than the fashionable component.**

~~~text
agent / reviewer / operator
    -> frozen task state + independent evidence
    -> task- and model-specific evaluation
    -> bounded action (tool / Git index / authoritative ref)
    -> deterministic status + validation
    -> inspect accepted result and recalibrate on real outcomes
~~~

## New things we can use now

### Reproducible AI code-review evaluation with ReviewBench

New canonical entry: [Evaluate AI code reviewers with grounded and augmented findings](../topics/ai/reviewbench-code-review-evaluation.md).

Copy the useful mechanics, not leaderboard marketing: pin base/head commits, label defects from multiple independent sources, score grounded known defects separately from novel valid ones, and slice by severity/category/cost. ReviewBench itself includes a reproducible 25-PR smoke set and 219-PR benchmark plus a container contract and judge; internal reviewer selection still needs our own Java/Spring-specific holdout.

### Narrow Git conflict staging with Git 2.56

New canonical entry: [Git 2.56: stage only resolved conflicts](../topics/platform/git-2-56-safe-conflict-staging.md).

Use `git add --resolved` as a deterministic post-edit guardrail for conflicted paths rather than using `git add -u` and silently picking up unrelated modifications. Keep staged-diff review, tests and merge gating after this step; the command does not prove semantic correctness.

## Valuable agent-system designs discovered

**ReviewBench (GitHub, October 5):** concrete, public offline review harness with frozen revision mirrors, multi-source candidate discovery, semantic deduplication, a uniform judge and severity/category slices. The code-review benchmark designer is also a code-review product vendor; its reported A/B agreement is useful but not independent proof of relative reviewer rankings. The reproducible dataset and runner are the real reusable pieces.

**NanoHarness empirical study (Hu et al., September 26):** controlled factorization of harness, model family and task class. More structured tools and narrowly task-specific subagents were generally more robust than generic fan-out. Context compression and general subagents were negative on some repository-generation tasks. This argues for *conditional* workflow topology, measured per task class rather than fixed by vendor defaults.

**GitHub Git infrastructure (October 6):** distributed-system design for a high-frequency agent write workload: keep consensus/coordination limited to reference updates, decouple compute and durable object storage, and move maintenance off the serving path. Internal benchmark claims of up to 35× write throughput are for their new storage architecture, not a portable performance estimate.

## Experiments worth trying

1. **Reviewer eval harness:** freeze 50–100 Java/Spring/Kotlin historical PRs with real known defects. Run a single reviewer, specialized scout/verifier, and ensemble multiple times. Compare high-severity grounded recall, augmented valid findings, developer interruption, latency and total review cost. Keep a private holdout to resist overfitting to the public corpus.
2. **Task-dependent harness ablation:** cross two model versions with three task types (localized bug fix, multi-file migration, repository generation). For each, toggle one of structured tools, compaction, general subagents and task-specific subagents. Publish success, retries, human repair time and token usage; retain only improvements with evidence on the intended work class.
3. **Safe Git conflict staging:** on a Git 2.56+ runner, exercise a dirty working tree with a conflict, unrelated changes, remaining markers and binary conflicts. Assert that `git add --resolved` stages only eligible conflicts and that semantic checks still catch bad resolutions.
4. **Workflow queue inventory:** instrument task creation, review, CI and merge queue wait age separately before expanding unattended coding-agent concurrency. GitHub's architecture write-up is a warning that scaling generation can simply move contention to another authoritative boundary.
