# KB intake — 2026-11-09

## Synthesis

The strongest lesson from this run is a refinement of our existing “put authority in the execution boundary” model: **the boundary must bind not only permissions, but also a specific *version of the evidence and code* used to make a decision.** GitHub Actions lockfiles make this literal for executable CI dependencies. The visible workflow can say `uses: owner/action@v3`, but the runner executes the lockfile's reviewed commit and verifies the source repository identity. That is a substantial improvement over telling a coding agent to “trust the CI”: CI itself has its own supply chain, often executing several layers of third-party code with broader privileges than the agent. The coverage limit matters as much as the improvement: reusable workflows, runner images and scripts downloaded at runtime remain distinct boundaries that still need explicit controls.

A second version problem lives **before the edit**. Coding agents often make bad changes because they could not find the code that defines an invariant, not because they cannot write Java or TypeScript. Entire Graph shows a useful, runnable design: build a local tree-sitter graph, rank definitions/callers/routes/impacted symbols and return bounded `file:line` evidence, plus an explicit report of parser gaps. It is tempting to treat this as “repository memory,” but that hides an important distinction: the graph describes a particular committed tree or worktree. If a search result comes from `HEAD` while another agent has modified a worktree, its findings may be obsolete. Even the tool's opt-in first-prompt context feature explicitly chooses the committed tree for speed, missing uncommitted edits. The right rule is therefore *retrieve candidates cheaply, verify against the exact revision and live source, and only then edit*. This expands our path-scoped instructions and evidence-gated edit principles without inflating model context with whole files.

GitHub's November 5 deep dive into Project Rubicon supplies a third, more distributed instance of the same principle. New object packs are durable in blob storage *before* one Ref-CAS transaction publishes both their manifest and reference updates. The replicated reference log issues version/LSN numbers; a cache can cheaply check whether its version is current and refresh only when needed. Background compaction runs independently of request-serving replicas, using leases and verifying that the merged pack has exactly the same objects before retiring inputs. The useful engineering principle is not “everyone should build GitHub's storage system.” It is that **immutable evidence, versioned mutable pointers, and independently verifiable publication/maintenance** let high-concurrency systems scale while retaining causal correctness. Our October 28 per-key CAS entry already described the high-level architecture; this source adds a concrete pack-manifest atomicity and compaction protocol rather than warranting a duplicate case-study page. GitHub's scale claim—5,000 concurrent agents and 7,200 pushes/second—is an internal test on a limited private preview, not a target for a normal service.

A few other findings helped set the admission bar. Entire's newly announced *Trails* moves evaluation history and merge gates to the center of its forge, an intriguing whole-system design, but its claimed throughput multiplier and automatic confidence scores are vendor measurements without a neutral quality study. Edera's OCAP model further clarifies the difference between identity and capability: a workload can prove who it is without possessing a broad credential in its environment. Those belong alongside our existing agent authority entries rather than another vaguely synonymous canonical page. Most revealingly, third-party PostgreSQL 19 articles advertise online checksum toggling, while the official PostgreSQL 19 RC documentation currently describes only offline enabling. That mismatch is reason to defer a production recipe, not to “average” the conflicting claims.

~~~text
coding agent proposes a change
  -> graph retrieval pinned to {repo, revision, worktree} + coverage
  -> read real source, verify callers/contracts and test
  -> commit / PR with exact head SHA
  -> CI executes reviewed, lockfile-pinned action identities
  -> trusted publisher validates status for that SHA and policy
  -> authoritative ref update with CAS; verify final committed state

shared rule: identity + version + independent evidence at every decision boundary
~~~

## New things we can use now

**Lock GitHub Actions dependencies with a reviewed transitive lockfile.** [Canonical recipe](../topics/platform/github-actions-transitive-dependency-lockfiles.md). Install the GitHub CLI `actions-lock` extension, generate `.github/workflows/actions.lock`, review the resolved commits (and owner/repo IDs), require `gh actions-lock --verify` in CI and let Dependabot update locked action references. Handle external reusable workflows and local actions explicitly. This is immediately relevant to any automated KB or coding-agent publisher running on Actions, and it is official GA functionality, not a speculative architecture.

**Give coding agents bounded, revision-aware source-graph navigation.** [Canonical recipe](../topics/ai/revision-bound-source-graph-navigation.md). Entire Graph provides a concrete OSS implementation with local semantic parsing, ranked source regions, call/impact queries and machine-readable parsing health. Put graph results behind `revision + coverage` and require source confirmation and tests. Evaluate on Java/Spring tasks against plain grep before enabling strict agent instructions or first-prompt injection.

## Existing KB entries improved

**Per-key write serialization with object-store replicas:** [updated entry](../topics/platform/per-key-write-serialization-object-store-replicas.md) now records GitHub's actual Rubicon write-read protocol: upload immutable pack, commit pack-manifest and reference mutations together in Ref-CAS, carry LSN/version checks on reads, and compact on separate leased shards with object-equivalence verification before manifest retirement. These are specific new implementation details absent from October's bridge article.

## Valuable agent-system designs discovered

**Entire / Trails (announced November 2026):** an agent-oriented Git forge where each push triggers cloud-sandbox review and risk/quality evaluations, successive runs retain visible score history, and unresolved findings/repository gates prevent merge. Continuous memory is built separately from a graph of source definitions/callers and checkpointed agent sessions. The architecture suggests a measurable *re-review until stable* experiment, not a reason to assume its automatic score is an independent correctness oracle. The vendor's reported 89× Git push speed claim must be reproduced under workload-matched conditions.

**GitHub Project Rubicon (November 5):** distinct durable payload layer (Azure Blob Storage), small replicated Ref-CAS for conditional mutable pointers and pack manifests, disposable read/write caches, and leased background compaction. This is a substantial systems case study with a strong invariant: a published pointer can never expose a pack not already durable; garbage collection must not race active readers. Private preview and internal load tests constrain generalization.

**Edera Bounded Authority (November 5):** SPIFFE/SPIRE identity, isolated agent execution and operation-scoped capabilities instead of broadly accessible credentials. The stated credential-brokered API path is not fully available yet; prototype credential-free command/API capabilities in a test environment and retain explicit execution-bound approval for sensitive actions.

## Rejected / deferred

- **PostgreSQL 19 online checksum SQL functions:** third-party beta writeups include a runnable story, but current PostgreSQL 19 RC official checksum documentation only specifies offline operations. Validate the exact GA/RC binary, built-in function signatures, WAL/replay impact and documented recovery behavior before recommending any in-place production conversion.
- **Entire Trails confidence scores and 89× throughput:** promising developer workflow, no independent correctness study and no apples-to-apples throughput baseline. Keep as a design/eval candidate rather than canonical claims.
- **JDK Project Babylon code-reflection-based AI models:** a useful direction showcased November 8, not a stable production Java API recipe for this KB.
- **AWS Lambda MicroVM + agent policy:** real architecture, but existing KB already covers deterministic containment, scoped tools and permission enforcement. Do not add article-summary duplication.
- **GitLab Duo composite identity:** strengthens the “identity versus authority” lesson; overlapping authorization/gateway guidance already canonical.

## Experiments worth trying

1. **CI dependency-lock dry run:** use a disposable workflow with direct and transitive actions, a mutable test tag and a reusable workflow. Check actual executed SHAs and that `gh actions-lock --verify` fails on stale/missing entries. Measure Dependabot review burden and lockfile rollout friction.
2. **Source-navigation ablation:** on 30 representative Java/Spring tasks compare grep only, Entire Graph explicit search, and first-prompt injection with identical model and budgets. Freeze a reference commit, then insert uncommitted changes to test staleness. Require actual code-path recall and successful tests, not just retrieval benchmark scores.
3. **Manifest/CAS crash test:** extend our toy Postgres + object store service with atomic `{ref, manifest}` transaction; inject crashes after payload upload and before/after CAS, and after compaction's output is uploaded but before old pack retirement. Assert no reachable ref points to missing payload, no lost updates and no prematurely deleted object.
4. **Merge-confidence calibration:** on historical agent PRs, record consecutive independent review scores *and* grounded known-bug recall (rather than score alone) across 3–5 iterations, plus review minutes and escaped defects. Decide whether score stability actually predicts useful reductions in human review work.
