# Run brief — 2026-11-09

The strongest idea today is **pin the thing you trust, not just the name of the thing**. That applies in three places a coding agent touches every day: the CI code that tests its patch, the repository snapshot it used to decide what to edit, and the shared ref that records whether its work was actually published.

The most immediately usable new primitive is GitHub Actions' **GA workflow dependency lockfile**. A workflow can still say `uses: some/action@v3`, but GitHub executes the reviewed SHA recorded under `.github/workflows/actions.lock`—including transitive action dependencies—and checks the upstream repository's numeric identity. The `gh actions-lock` CLI extension creates it; `gh actions-lock --verify` checks for stale entries; Dependabot updates the corresponding entries in normal action upgrade PRs. This isn't the same as making the whole build deterministic: external reusable workflows, downloaded scripts, container images, secrets and runner images have their own authority boundaries. A concrete first step for any agent-assisted GitHub workflow is to pilot lockfiles in one low-risk workflow and verify the exact executed action commit before and after a deliberately moved tag.

The second find, **Entire Graph**, solves a subtler coding-agent problem: the agent wastes time searching whole repositories and can overlook callers or invariants before changing a method. The open-source graph uses local tree-sitter parsing, ranks source regions and exposes definition/caller/impact relations with file-line references. A useful retrieval contract returns the repository revision, parser coverage and bounded results, then requires the agent to read actual code and test before touching it. It is important not to confuse a graph with living code: Entire's opt-in first-prompt injection uses committed `HEAD` and does not include uncommitted worktree edits. Its vendor-reported LoCoMo score and up-to-71% token savings need validation on real Java/Spring task outcomes; the vendor's own paired first-prompt tests were statistically inconclusive. Start with a small agent ablation, not a mandatory graph-only rule.

GitHub's November 5 **Project Rubicon** engineering account deepens a pattern we already captured in October. For concurrent writes, payloads go durably into object storage first, and one small Ref-CAS transaction atomically publishes the pack manifest and ref change. Every accepted mutation gets a log sequence number that a read replica can use to check whether it is current. A separate leased compaction fleet verifies new output packs contain exactly the same objects before removing older manifest entries. GitHub reports 7,200 pushes per second with 5,000 agents in internal tests, while production rollout remains a limited private preview. We updated the existing per-key write serialization page with these new mechanics instead of adding another article summary.

There were also two useful “not yet” results. Entire's new Trails forge keeps successive agent review/quality scores and gates visible on each push—worth an experiment to see whether repeated review really stabilizes correctness, but a vendor confidence score is not the same as a known-bug oracle. Edera's bounded-authority design is a clear reminder to keep both credential material and broad privileges outside agent sandboxes; much of its planned API brokerage is still being rolled out. And although third-party articles describe online data checksum conversion in PostgreSQL 19, the current official RC documentation still describes only offline enabling. That discrepancy is a reason to verify the released server before writing a production runbook.

**What I'd test next:** (1) transitive GitHub Actions lockfile coverage including external reusable workflows; (2) repo navigation using grep versus graph on real Java/Spring edits with dirty worktrees; and (3) CAS/manifest crash injection with two independent writers and background compaction. The common measure is not the elegance of a pattern but whether it produces a version-bound, independently verifiable outcome.
