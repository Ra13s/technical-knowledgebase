# Run brief — 2026-09-18

The clearest theme in this run is that **organizational knowledge becomes much more valuable when it is packaged as an executable capability instead of passive context**. LinkedIn CAPT, DoorDash Flux and Spring AI Community Agent Skills independently converge on the same architecture: expose a small amount of metadata first, let the agent discover the relevant workflow on demand, then load the detailed instructions/tools only when that workflow is selected. The useful abstraction is not “put more company documentation into the prompt.” It is “turn recurring expert procedures into versioned workflow contracts.”

That distinction gives us a cleaner boundary between knowledge, judgement and authority. A playbook can encode how an organization investigates an incident, cleans up an experiment or performs a migration. The model still supplies judgement inside the workflow. But the surrounding system decides what inputs exist, what tools may be used, which deterministic checks are mandatory and which side effects need approval. This is more reusable across IDE, background-agent and scheduled surfaces because the workflow definition becomes a deployable capability rather than a giant copied prompt.

LinkedIn's CAPT is especially interesting because it combines central and repository-local playbooks and hides a large tool estate behind a small set of meta-tools for discovery/inspection/execution. DoorDash Flux reinforces the permission boundary: the playbook declares required capabilities, while a gateway actually grants scoped access and logs actions. Spring AI's community SkillsTool gives us a concrete Java implementation option for progressive skill discovery, but it should remain only the discovery/execution interface; sandboxing and permission enforcement still belong outside the skill itself.

Datadog DODO contributed a separate but related lesson: **a deterministic gate is only useful if its oracle represents reality**. Their optimization workflow first builds a benchmark from production-derived inputs and profiler shape, iterates until that benchmark resembles production, then freezes it before the optimizer is allowed to edit service code. That upgrades the existing search-based optimization entry from “correctness + benchmark” to “validate the benchmark, freeze it, then search.” Otherwise an optimization agent can become very good at gaming a synthetic fitness function that does not matter in production.

The two non-agent platform findings share the same migration philosophy: preserve the consumer contract while changing the backend. Java 26 exposes HTTP/3 through the familiar java.net.http.HttpClient, so a service can canary H3 and inspect the negotiated response version instead of replacing its HTTP stack. Kubernetes 1.37 can satisfy an existing extended-resource name through DRA, allowing node-by-node migration without forcing every workload to adopt ResourceClaim immediately. In both cases the useful move is **preserve the contract, change the implementation boundary, measure what actually happened**.

## What I would try next

Take one real recurring internal procedure that currently lives in a checklist or tribal knowledge and turn it into a playbook with explicit inputs, tools, permissions, validation and outputs. Compare it with a free-form prompt on the same tasks and measure context size, tool mistakes, review effort and success rate.

For code optimization, pick one CPU hotspot, build a benchmark from sanitized real inputs plus profiler call-shape evidence, freeze it once it is representative, then compare one-shot optimization with bounded search. For platform follow-ups, canary HTTP/3 against one external endpoint and record the actually negotiated protocol, or migrate one accelerator node pool to DRA while leaving workload manifests unchanged.
