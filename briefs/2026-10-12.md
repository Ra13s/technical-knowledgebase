# Run brief — 2026-10-12

The most useful idea today is that **autonomous engineering needs a better boundary between uncertain judgement and authoritative effects**. We already have good rules for how a coding agent should gather evidence and how its actions should be validated. This run adds a missing piece: when we say one reviewer or agent architecture is “better”, what exactly did we measure, and did the evaluation reward the correct behavior? Conversely, when an agent makes a real mutation to a repository, how can we make that step *narrower*, so uncertainty about the judgement does not accidentally widen its impact?

GitHub's newly released ReviewBench is the strongest immediately reusable find. Instead of trusting a handful of manually chosen pull requests, the benchmark uses 219 real PRs from 187 repositories across 19 languages, fixed base/head commits and a known-issue set assembled from multiple sources: historical human reviews, follow-up fixes, static analysis and multiple models. It semantically deduplicates claims and uses an independent common judging rubric. This is a much stronger starting point for evaluating an AI reviewer than counting comments or asking another model whether it liked the review. GitHub says its golden labels matched independent senior engineers 96.6% of the time; that is encouraging, but the benchmark and Copilot review product still come from the same vendor.

The best detail is **grounded versus augmented scoring**. Grounded recall answers a stable question: did the reviewer find the defects we already know about? Augmented metrics allow a reviewer to get credit for a valid issue that nobody happened to put in the original reference set. We need both, because a supposedly “golden” code-review dataset is never complete. There is an important catch: augmented recall changes its denominator with each reviewer's novel findings, so it should not be used as a direct leaderboard comparison. For our own reviewer, this means creating a smaller, private Java/Spring-heavy set of real PRs and measuring category/severity-specific findings, false positives, human review effort and cost alongside any public benchmark.

The independent paper *Beyond the Model* changes how I'd run our harness experiments. Its authors compared ten models, two harness designs and three software-engineering task families, then tested individual components such as structured tools, planning, context compression and subagents. Structured tools and task-specific subagents were relatively dependable improvements. But generic subagents and compaction could hurt repository-generation tasks. Stronger models also needed less scaffolding on some localized repair work. The practical takeaway is not that compression is bad or subagents are good; it is that **a model upgrade must be evaluated against several task families**. We should not take a win on SWE-style repairs as evidence that the same harness is correct for a complex migration or greenfield application.

The less glamorous but immediately useful discovery was Git 2.56's `git add --resolved`. It adds only paths that are currently unresolved in the Git index and contain no remaining textual conflict markers; when it spots markers among the selected files, it refuses to stage any. That prevents a conflict-resolution agent from blindly staging unrelated local edits with `git add -u`. It is not magic: an incorrectly resolved Java method may contain no conflict markers, binary files have none, and already staged changes remain. The right workflow is constrained staging, then staged-diff inspection and deterministic tests—not automatic trust in a successful Git command.

GitHub's October 6 infrastructure post gave a larger-scale architecture example: when thousands of agents push and CI fetches concurrently, repository write acknowledgement, central ref updates and maintenance become bottlenecks. Its proposed design coordinates only the part that genuinely needs serialized agreement—the ref update—while parallelizing object work and separating durable storage from caching workers. That is valuable background and a possible future case study, but not yet a turnkey recipe for our own systems; I kept it out of canonical KB rather than manufacturing a page from a company's design announcement.

## What I'd try next

For the review workflow, select 50 historical internal PRs with known real defects and run the current reviewer, scout-plus-verifier and a multi-model ensemble on the same frozen base/head SHAs. Compare actual severe-issue recall, valid novel findings and the cost of interrupting developers—not only headline F1. For agent harnesses, run one ablation matrix across localized fixes, cross-file migrations and fresh module creation with a model before and after an upgrade. For the Git side, add a `git add --resolved` integration test with a dirty worktree and an intentionally bad conflict resolution, proving that it constrains staging without replacing tests.
