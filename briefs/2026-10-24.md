# Run brief — 2026-10-24

**The strongest discovery is that agent permissions need three different enforcement layers, and they must agree on the same operation.** A model might say “I am only investigating,” but its shell process can still read a secret, its MCP client may discover a deployment tool, and its network client can still send an authorized-looking request to the wrong account. The remedy is not a longer AGENTS.md: it is an OS limit on what the process can reach; a policy engine outside the model deciding which *actual tool call* is permitted; and target-side authorization with a credential scoped to that identity. Useful traces come afterward, but they cannot turn an unchecked action into a safe one.

AWS's new [Strands Box](../topics/ai/operation-level-agent-sandbox-policy.md) is particularly interesting because its Dogwood policy language can examine the **history of tool events**. A rule can permit a Slack message until three successful posts occurred in ten minutes, or block an outbound action after a sensitive event. The catch is more informative than the product name: the preview runs on **macOS Apple silicon**, and direct file access granted by its sandbox does not necessarily emit Dogwood events. A temporal rule is only trustworthy when all relevant actions cross an instrumented boundary. We should test what the policy engine really observes with adversarial shell/Python/MCP calls before adopting any claim of cross-tool protection.

Eon's production [identity-aware MCP gateway](../topics/ai/identity-scoped-mcp-gateway.md) solves the organizational half. Developers using different IDE agents and one autonomous SRE agent share a single tool URL, but people authenticate by corporate SSO while bots use service identities. Every `tools/call` passes a Cedar authorization rule, and target-side credentials are handled by the runtime/gateway rather than by dozens of local MCP processes. The subtle scaling lesson: putting hundreds of tools into one pre-indexed policy can exhaust its size quota. Eon switched large targets to dynamic tool enumeration—less policy size, but also no semantic search on those targets. **Discovery and authorization are different APIs**; hiding a tool is not enough if it remains callable by name. Eon's reported improvement from days to minutes of onboarding is encouraging but is a first-party account of one AWS deployment.

The [OpenTelemetry agent-observability sample](../topics/ai/external-authoritative-agent-telemetry.md) gives us a practical way to debug all this. Propagate a W3C trace from an agent through its LLM gateway, add a collector for batching and consistent export controls, then correlate the span with the **external executor's** decision and result. We should treat a model-originated “tool succeeded” span as intent/evidence, not a substitute for GitHub's actual PR, Kubernetes' actual deployment state or a database write receipt. This extends our prior work on authoritative telemetry and crash recovery rather than creating another generic observability page.

The surprise of this run was a conventional SQL/API optimization from GitHub's star-history redesign. Before the change, reconstructing React's growth curve meant around 2,511 HTTP requests. But simply replacing that with a paginated `GROUP BY` over all stars would still scan the full table again for every page. The better rule in the new [time-window-first aggregation recipe](../topics/platform/time-window-before-aggregation.md) is to constrain an indexed, half-open `created_at` range **before** grouping daily counts. A response limit is not a database-work limit. Its resulting curve also has a particular contract: it counts stars still present, not every historical star addition. That is exactly the sort of caveat that should live beside the command or query somebody will copy.

**What I would test next:** a three-principal MCP ACL matrix with a deliberately discoverable but forbidden write tool; Box/Dogwood event-history coverage on a supported Mac; an OTel trace in which the agent reports success but the executor fails; and a PostgreSQL benchmark on skewed, high-volume date windows. Separately, OpenAI's October Cosmos DB write-up and Spotify's repository-wide agent migrations look valuable, but they need focused experiments or a specific new decision rule before another canonical entry.
