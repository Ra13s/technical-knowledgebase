# Run brief — 2026-09-22

This run pushed a recurring KB theme into a more general rule: **important autonomous claims need explicit identity, proof and lifecycle state**. “The model found a vulnerability”, “the request returned 200” or “the CRD was updated” are all weak statements when downstream state matters. The useful design move is to represent the claim as something that can be independently checked, scoped and observed through completion.

Google's pre-submit security work and Mantis were the clearest examples. An LLM finding starts as a hypothesis, not as a trusted defect. A stronger pipeline localizes threat context, performs cheap discovery, then uses a distinct structural triage stage to inspect AST/call-graph/domain evidence. Expensive or high-impact findings can move into sandbox reproduction with explicit acceptance criteria. Only then does a patch agent receive the evidence, and the resulting fix has to survive the original reproducer plus adversarial retesting. The important architecture property is **role separation**: the component that invents a finding does not get to declare it true.

That became a new proof-gated security review pattern in the KB. It is stricter than “use another reviewer model” because the second stage is expected to attach concrete evidence: entry point, sink, reachable path, reproducer, or a deterministic domain rule. This is exactly the kind of pattern worth copying into other agent domains. A code-review finding, migration claim or incident diagnosis should become more trusted only as independent evidence accumulates—not because several agents agree.

Datadog exposed a different failure mode: at fleet scale, **recovery itself becomes load**. A retry policy that is safe for one agent can overwhelm a model provider, CI farm, sandbox pool or downstream API when hundreds of runs retry simultaneously. So agent capacity planning must cover the full trajectory, not only LLM quotas. Requests should carry workload, owner, environment, service class and run identity through every queue and enforcement point. Recovery needs two budgets: one bounding how much a single trajectory can amplify, and another bounding aggregate concurrency/queue pressure on the shared dependency.

Kubernetes 1.37's StorageVersionMigration was a conventional-platform example of the same principle. Updating a CRD's storage version or rotating encryption state does not mean existing objects have been rewritten. The new stable migration API makes that hidden work a first-class resource with observable completion. The safe rule is to wait for Succeeded=True and verify stored-version convergence before removing the old API version; if the CRD changes during migration, rerun instead of inferring success from configuration.

Also trace one task end-to-end and confirm workload/owner/environment/service-class/run identity survives success, rejection and retry paths.
