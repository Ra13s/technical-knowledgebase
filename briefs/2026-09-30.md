# Run brief — 2026-09-30

The strongest idea from this run is simple: **profile the work before deciding what to optimize**. Once an agent system is already capable of completing useful tasks, the next bottleneck is often not the model itself. Cursor's production harness work, AgentPProf's cross-run profiling approach and Augment's software-factory write-up all point in the same direction: look at where tokens, wall time, retries and queueing actually accumulate across many runs, then change the bottleneck you can demonstrate rather than the component that is easiest to measure.

This sharpens the existing agent-fleet-unit-economics guidance. “Cost per accepted outcome” is still the right top-level metric, but it needs a profiler underneath it. A trace is good for explaining why one session failed. It is much weaker for deciding whether the fleet is wasting most of its effort on repeated code exploration, oversized static tool schemas, cache-unfriendly request layout, test repair, or waiting for review and CI. The new semantic trajectory profiling entry gives us a concrete way to aggregate many sessions by task/skill/phase/action and weight them by tokens, time or effects. The practical rule is: **trace to debug one run; profile to decide what to optimize across runs**.

Cursor's production data adds a very concrete harness lesson. Stable, frequently reused context should stay small and early in the request so caches can actually help; variable setup should come later; low-frequency tools should be progressively disclosed instead of serialized into every call. Cursor reports a roughly 66% reduction in system-prompt size, a 60% reduction in static built-in-tool description tokens, 20% fewer cold cache misses, and about 7% lower overall token cost without measured quality loss in its workload. Those numbers are vendor- and workload-specific, but the engineering method is reusable: change request shape, A/B it on representative traffic, and measure cost, latency, cache misses, tool errors and task success together.

Augment adds the next systems-level step: **queue growth is inventory**. If code generation becomes much faster, the bottleneck can move into review, CI, verification, deployment or feedback triage. Continuing to optimize generation after work starts piling up elsewhere is local optimization. Their reported 17,200-PR longitudinal dataset shows large improvements in output, merge time and revert rate, but they explicitly do not claim a controlled causal result. The useful part for us is the operating model: graph queue depth, oldest-item age, wait time and rework at major workflow boundaries, then automate the largest persistent queue rather than blindly adding more agents.

Two narrower platform findings also made the cut because they translate directly into implementation changes. JDK 27 now supports in-process JFR redaction for selected startup arguments, environment variables and system properties. That lets us remove common sensitive values before supported events ever leave the JVM, but it is not universal sanitization, so the correct rollout pattern is to preserve runtime defaults, add only small organization-specific patterns, and canary-test actual recordings. Kubernetes 1.37's HPA scale-to-zero is similarly useful only when the wake-up signal exists independently of running Pods. For queue workers that means External/Object metrics plus durable pending work; CPU/memory-only HPAs cannot wake themselves from zero.

## What I would try next

Start with one real agent workflow and freeze 50–100 completed sessions. Produce token and wall-time semantic profiles, identify one clearly wide stack, make one harness change, and rerun the same workload. In parallel, add oldest-item age and wait-time metrics at task → PR review → CI → verification boundaries; that will tell us whether the next optimization belongs inside the agent loop or outside it.

For platform follow-ups, add a harmless canary-value test to one JDK 27 JFR rollout and run a zero-to-one drill for one non-critical queue worker on Kubernetes 1.37.
