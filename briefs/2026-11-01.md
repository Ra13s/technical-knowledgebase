# Run brief — 2026-11-01

**The practical lesson: the code-generating agent should not be the authority that publishes its own changes.** GitHub Agentic Workflows can compile an agent's natural-language task into GitHub Actions, run the model with a read-only repository view, then pass a structured proposed write to a separate Safe Outputs job. That trusted stage checks the operation type, destination, file allowlist and write budget before creating a PR. The model's useful creativity and the executor's permissions are deliberately different things.

This was more than an abstract security recommendation. Microsoft Aspire used exactly this architecture to keep product documentation in sync across two repositories. A merged feature PR causes a deterministic resolver to pick the appropriate docs release branch. An agent reads the diff, linked issues and doc-writer guidance, and creates a draft docs PR whose reviewer is the original feature SME. In a 30-day sample covering releases 13.3 and 13.4, the team reported 396 source PR events, 82 documentation PRs, all 82 ultimately merged, and a 44.8-hour median merge time. These are internal, observational metrics and include human review—not a promise that unsupervised merging is safe. But the separation is worth copying, especially for our KB, where discovering a useful source and reliably publishing the resulting change have proved to be distinct problems.

The security research made the boundary even more concrete. A paper on **Agentic Workflow Injection** distinguishes ordinary *Prompt-to-Agent* paths (untrusted issue text manipulates an agent with tools) from *Prompt-to-Script* paths (the model produces output that a later CI script interprets as an executable instruction). The authors' static/data-flow study reported 496 exploitable cases from 519 flagged workflows under their test conditions. We should not use that number as an industry-wide compromise rate or assume the scanner is validated for our environment. The reusable practice is to keep model output tainted, validate schema and authorization outside the model, and never interpolate generated text directly into privileged shell commands. I added a source-to-sink inspection and regression-testing recipe.

On the Java/platform side, **Temporal Standalone Nexus Operations**, entering Public Preview on November 1, offers a simpler way to make a *single* durable cross-service call directly from a normal Java backend. With Java SDK 1.36.1+ and Temporal CLI 1.9+, a client can start a named Nexus operation and retrieve the result later by handle without creating a proxy Workflow. The same Nexus service contract works when called from Workflows. The important limitation is at-least-once execution and experimental APIs: the app still needs stable IDs, handler idempotency and a DB-to-operation recovery plan.

Finally, GitHub's code-review team published a useful negative experiment: replacing bespoke reviewer navigation tools with general `grep`, `glob`, `view` initially made reviews worse. After explicitly shaping the instructions around diff-first searches and bounded evidence reads, GitHub reported around 20% lower average review cost at equivalent quality. We added that detail to the existing code-review page. A tool upgrade is only good if the *trajectories it creates* are better.

The actionable next step is to test a **GitHub-side safe-output publisher in a separate test repo** against the current external connector. We should measure completed PRs and duplicate prevention rather than counting generated Markdown files.
