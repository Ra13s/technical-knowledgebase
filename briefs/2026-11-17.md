# Run brief — 2026-11-17

**The most valuable idea this run is that successful autonomous engineering needs independent evidence before and after the change.** Not a second model agreeing with the first, but a separate authority that can actually reject its work: a reference API, a known requirement, a verified production trace, or a deterministic Git/CI boundary. Three very different 2026 systems expose that pattern: AWS's agent-built API emulator, Google's agent-quality investigator and Uber's runtime intent controls. They are useful for different reasons, but all preserve evidence that an agent's narrative cannot silently edit.

AWS Emulator, made public November 11, has an unusually concrete large-scale agent development design. The first team constructs realistic AWS scenarios from Smithy API models and verifies them against actual AWS. The second team replays those accepted tests against an emulator and records distinct failures. The third repairs one bounded issue at a time, behind independent build, security, review and fidelity gates. The reusable insight is **not** AWS's headline of hundreds of agents and thousands of fixes per day; that is a first-party workload-specific claim. It is the custody and replayability of a reference-validated test corpus. In this environment, an agent cannot simply rewrite the test oracle until its own implementation passes. That connects directly to our existing work on independent mutants for agent-generated tests and deterministic agent orchestration.

Google's AQuA answers the complementary question: what happens when a deployed agent returns HTTP 200, has good latency and no tool errors, but silently fails the user's intent? Its out-of-band pipeline samples traces, finds actual/expected discrepancies, groups repeats, sends candidates to an independent verifier, and diagnoses only against the immutable source and instructions that generated the trace. It cannot patch the production agent itself. In Google's **scripted 32-session experiment**, nine initial issue clusters were reduced to six verified issues, and two small prompt changes improved targeted outcomes. That is interesting evidence for a diagnostic method, not an independent demonstration of production recall. We should preserve both true positives and missed critical cases as evaluation metrics.

The immediate Java/Spring finding is **AWS Emulator as a real-SDK local integration target**. It launches isolated local HTTPS/SigV4 endpoints with short-lived emulator credentials and in-memory state. Test code can talk to an AWS-shaped service without setting up an AWS account. Java requires a special PKCS12 trust store, and the test must verify its account is the emulator account `000000000000`, not accidentally real AWS. We have a new recipe and a proposed comparison with Mockito and an isolated AWS sandbox. Crucially, unsupported operations return 501 and the fidelity report is incomplete; this does not replace real AWS provider testing.

Security added two different constraints. First, Git's **November 10, 2026 security release** patched six vulnerabilities, including recursive-clone code execution and unsafe merge/patch behavior. Our older Git 2.56 conflict-resolution recipe now specifies **2.56.1+**, and CI/agent runners must be audited for bundled Git binaries. Second, Uber's November 6 article explains why a permissible API call can still be inappropriate to the user's actual request. The extra check correlates tool actions with registered agent intent and authenticated instruction provenance, then calibrates semantic detectors per agent in shadow mode. It complements but must never overrule deterministic IAM, permission and sandbox checks.

The cross-source lesson is **versioned evidence across a bounded decision loop**. Test-writer evidence must describe the real reference version; a fix must be validated at the exact candidate commit; production traces must identify the exact deployed source and tools; authorization must apply at the actual operation boundary. Where there is no independent reference, human-authored contracts, adversarial testing and human review carry more of the load. Adding more agents to a loop without fixing those evidence contracts mostly accelerates uncertainty.

## What I'd try next

Start with **20 reference-validated stateful tests**, then run isolated agents for test discovery, issue finding and repair against a tiny compatibility service. Compare the hidden-test defect escape and reviewer burden to a single agent doing everything. In parallel, pilot AWS Emulator with one Spring service and explicit failure if real AWS credentials are present. Finally, run an out-of-band AQuA-style review over 200 sanitized agent sessions with known silent failures, and verify that proposed code citations really point at the deployed revision.
