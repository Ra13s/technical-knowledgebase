# Gate coding-agent harness configuration as a supply chain

## What it is

Treat persistent coding-agent configuration — instruction files, skills, commands, hooks, MCP declarations, subagents and permission files — as an executable dependency layer that needs deterministic validation before installation and again after components are assembled in a repository.

The key distinction is **collection-time vs setup-time risk**. A downloaded skill can already contain unsafe tool pre-approval or malformed metadata, while other defects only appear after it is combined with project settings, MCP declarations and permissions.

## Use when

Use this whenever a repository commits or installs coding-agent configuration such as:

- `AGENTS.md`, `CLAUDE.md`, Copilot instructions or Cursor rules;
- reusable skills or commands;
- hooks and subagent definitions;
- `.mcp.json` / MCP server declarations;
- tool allowlists, permission modes or agent-local settings.

Especially use it when agent configuration is copied from marketplaces, shared team repositories, examples or generated by another agent.

## Core rule

**Lint the harness itself, not only the code the harness produces.**

Run deterministic checks at two boundaries:

```text
third-party skill / bundle
        |
        v
install-time gate
  - parse required metadata
  - expose/prevent broad tool grants
  - inspect embedded scripts
        |
        v
assembled repository harness
  - pin executable dependencies/MCP servers
  - validate project permissions and hooks
  - check paths/references that are decidable from the tree
        |
        v
CI gate + normal agent runtime controls
```

Do not assume that a marketplace/recommendation list constitutes review. Also do not assume a clean individual skill means the assembled project configuration is safe.

## Concrete check with `harness-eval`

The open-source `harness-eval` tool currently supports Claude Code, Cursor, Windsurf, Cline, Copilot, Gemini CLI, OpenCode and Codex layouts.

```bash
pip install harness-eval

# broad deterministic inspection
harness-eval harness-lint .

# only validated gating-tier rules; exits non-zero on a finding
harness-eval harness-gate .

# security-focused scan
harness-eval harness-security .

# inspect a downloaded skill before installation
harness-eval skill-verify ./downloaded-skill
```

For incremental adoption, create a baseline rather than making a noisy first scan immediately fatal:

```bash
harness-eval harness-lint . \
  --format json \
  --output .harness-eval-baseline.json

harness-eval harness-lint . \
  --baseline .harness-eval-baseline.json
```

SARIF output is also available for CI/code-scanning integration.

## High-value rules to implement even without this tool

### Pin runtime-loaded tool dependencies

Avoid declarations whose executable version floats with time, for example:

```text
npx -y @scope/mcp-server
uvx some-mcp-server
docker run vendor/server
```

Prefer an exact package version, lockfile/digest or another reproducible resolution mechanism. The September 2026 empirical study found unpinned MCP packages in 9.8% of analyzed assembled setups.

### Treat interpreter grants as arbitrary execution

A permission that looks narrow may still provide a general interpreter:

```text
Bash(python:*)
```

If arbitrary Python can run, the effective capability is arbitrary code execution. Permission review should reason about the semantic capability, not only the string prefix.

### Make skill tool grants visible at installation

A reusable skill that declares broad `allowed-tools` can import authority into every repository that installs it. Surface those grants before installation and prefer scoped forms rather than silent shell pre-approval.

### Validate required metadata at load time

Reject or loudly report malformed/underspecified skill or subagent definitions instead of letting each client improvise different defaults.

## Gate only what is sufficiently decidable

A static condition is not automatically a defect. The empirical study found that pairwise differences such as two assistants having different context files were often intentional.

Use three classes:

```text
exact + consequence validated  -> CI gate
exact but consequence contextual -> warning/review
heuristic/prose judgment       -> advisory or separate semantic review
```

This matters because a noisy security gate trains developers to ignore the gate.

## Why it is useful

A September 2026 study of 3,171 public GitHub repositories found confirmed security defects in 16.0% of 2,660 assembled agent setups. The strongest measured problems were ordinary configuration hygiene failures rather than exotic model attacks: unpinned MCP execution, scoped-looking arbitrary-execution grants and reusable skills that pre-approved shell access.

The practical lesson is familiar from package management and IaC: once configuration can cause privileged execution, it deserves versioning, static analysis and CI policy.

## Caveats

- The study used public repositories and model-assisted adjudication; its percentages are evidence of material prevalence, not an expected defect rate for every organization.
- `harness-eval` contains advisory/heuristic rules in addition to validated gating rules. Do not fail CI on every warning blindly.
- Static analysis cannot prove runtime behavior or resistance to prompt injection. Pair this with sandbox/runtime tests.
- Version semantics move quickly. A rule about a client-specific permission must state which client/version makes the consequence true.
- Cross-component graph analyses are promising, but the study found that several mechanically detectable cross-file differences did not meet a high-confidence consequence bar.

## Prototype experiment

On 10 repositories that contain agent configuration:

1. run `harness-gate` and `harness-security`;
2. classify findings into exact defect / contextual / false positive;
3. fix unpinned runtime dependencies and broad interpreter grants first;
4. add the exact validated subset to CI;
5. run `skill-verify` on any new third-party skill before installation.

Track findings per repository, false-positive rate, time-to-fix and whether later harness changes reintroduce the same class.
